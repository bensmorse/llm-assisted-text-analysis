LLM-Assisted Analysis of Open-Ended Text

Consumer Car Reviews from Edmunds.com

Intro

Companies commonly collect unstructured textual data containing insights into consumer preferences and behavior. Common examples include customer reviews, feedback surveys, support tickets, or transcripts from focus groups. Historically, coding and analyzing these data has been challenging, in part because traditional topic modeling or natural language processing methods are complex, opaque, and not always insightful. The advent of LLMs, however, has dramatically simplified the process of analyzing unstructured text and improved the quality of the resulting output.

This page provides a demonstration of the process by which LLMs can be used to code and quantify unstructured textual data. The process involves four steps:

  1. Define the codes (variables) that will be used to classify the unstructured textual data.1
  2. Using your preferred LLM’s API, submit the unstructured textual data to the LLM alongside prompts for each code. Specify that results be returned in JSON format.
  3. Validate the accuracy of the resulting LLM-coded output against a small subset of human-coded observations. If necessary, refine the prompts and/or codes and repeat steps 1-3 until an acceptable accuracy level is reached.
  4. Analyze the resulting quantitative data as desired.

Data

We’ll use data on car reviews scrapped from Edmunds.com and made publicly available on Kaggle. For each review, we have data on the date the review was submitted, vehicle brand, review text and title, and the customer’s overall satisfaction rating on a scale of 0 to 5 for. The data cover approximately 206,000 reviews submitted between 2004 and 2018. The goal is to code the sentiment of each review (setting aside for time being that we already have reviewers’ numeric satisfaction rating), as well as various metrics that we might be interested in tracking overtime, such as whether the reviewer references the vehicle’s reliability, safety, drive characteristics, or other variables of interest.

Define the prompts that will be used to code the data:

prompt<-paste("Please car review the an owner submitted to Edmunds.com, a popular website for reviewing cars. Review the response carefully and code the following variables:")

response_coded <- type_object(
  prompt,
  sentiment = type_enum("Extract the sentiment of the review", c("positive", "neutral", "negative")),
  gpt_Rating = type_number("Based on this review, how do you think the owner would rate their vehicle? Use a numeric scale from 1 to 5, where 1 is very negative, and 5 is very positive."),
  reliability = type_integer("1 if the owner references the vehicle's reliability in their review, 0 otherwise"),
  utility = type_integer("1 if the owner references the vehicle's utility features in their review, 0 otherwise"),
  driving = type_integer("1 if the owner references the vehicle's driving characteristics in their review, 0 otherwise"),
  comfort = type_integer("1 if the owner references the vehicle's comfort in their review, 0 otherwise"),
  interior = type_integer("1 if the owner references the vehicle's interior features in their review, 0 otherwise"),
  fuel_efficiency= type_integer("1 if the owner references the vehicle's fuel efficiency in their review, 0 otherwise"),
  technology = type_integer("1 if the owner references the vehicle's technology features in their review, 0 otherwise")
)

The next step would be to loop through the entire corpus, coding each observation one-by-one. However, with over \(206,000\) observations and about 2 seconds for each query to the API, this code would take about 5 days to run. For purposes of this demonstration, we’ll use a sample of \(7,000\) randomly sampled observations:

# code a subset of responses
df.sub <- df |>
  slice_sample(n = 7000)

result = NULL
for (i in 1:nrow(df.sub)) {
  out <- chat$extract_data(paste(df.sub[i,"Review"]), 
                          type = response_coded)
  result <- rbind(result,
                  cbind(df.sub[i,"index"],as.data.frame(out)))
}
glimpse(result)

A few interesting trends are evident. First, driving characteristics and reliability remain the most commonly-referenced characteristics throughout the period, suggesting that consumers highly value these characteristics. Second, comments regarding a car’s technology have steadily increased overtime, from a low of 11% of reviews in 2002 to roughly 35% of reviews by 2018. Were the data to cover the present period, I would expect this figure to be even higher. Lastly, references to fuel economy closely mirror long-term oil prices:2 references spiked in 2005-06, following a jump in oil prices to above $80 per gallon. Oil prices (and references to fuel economy) remained elevated through 2014, whereafter we saw a drop to below $60 per gallon.

According to GPT, 70% of reviews were positive, 24% were negative, and 6 % were neutral. Disaggregating results by positive vs. negative review, a number of interesting patterns emerge:

For negative reviews, by far the most frequent complaint relates to reliability. To a lesser degree, unsatisfied customers complain about faulty technology, or unpleasant driving characteristics. Surprisingly, they don’t seem to complain too much about poor fuel economy. For positive reviews, satisfied customers most commonly praise the vehicle’s driving characteristics, followed by comfort and reliability. References to technology have increased overtime, but remain subordinate through 2018, the latest year for which data are available.

Accuracy of LLM-Assisted Classification

We’ve coded the data and summarized the results, but how confident should we be in the accuracy of GPT’s coding? In a real-world application, the best way to verify the accuracy of LLM-coded data would be to compare LLM-generated codings to a small, randomly-selected test set of human-coded reviews.3 But since this is just a demonstration, we won’t go through the process human-coding. Instead, as prime-facie validity test, we can take advantage of the fact that reviewers provided a 1 to 5 satisfaction rating alongside their review, which we can compare to GPT’s predicted customer satisfaction based on its reading of the review.4 (This test is actually a little unfair to GPT, since customers’ overall ratings may have differed from the focus or topic of their review.)

The root mean-squared error (RMSE)5 for the GPT-generated ratings is 1.1, which suggests that on average, GPT’s rating was within 1.1 points (‘stars’) of the customer’s rating.

# calculate rmse

rmse <- sqrt(mean((df.coded$Rating - df.coded$gpt_Rating) ^ 2))
round(rmse, digits=2)
